## D2 alumno projection (exact)

Every alumno block in the `formulario`, `historial` and `fichaSocioeconomica` payloads must pass `alumnoLocal` (`shared/mi-informacion-wire.mjs:259-264`). The fields and their values:

- **Identity:** `codAlumno=actorId`, `nomAlumno=actor.name`, `apePaterno=''`, `apeMaterno=''`.
- **Period and scope:** `periodo='2026-2'` (legacy form of scope `2026-II`), `desFacultad=scope.facultyId` (`'FISI'`), `desEscuela=scope.schoolId`, `codPlan=scope.planId`, `desPlan=scope.planId`.
- **Specialty:** `desEspecialidad='No disponible'`. The draft's `''` fails `nonEmptyString`.
- **Numbers:** `ponderado=actor.ponderado`. Every other number is `0`, including `codFacultad`, `codEscuela` and `codEspecialidad`. The draft's codes 20/1/2 looked like official codes, and they are only read by the legacy plan validator, which this mode does not use.
- **Remaining fields:** other strings `''`, all booleans `false`.

`formulario`: `formulario: {}`, sections from the existing builder with null values, and all flags `false`. `historial`: empty (`approvedCourseIds=[]` and `failedCourses=[]` are true fixture facts). `ficha`: existing builder, `familiares: []`. `evaluaciones`, `deudas`, `asistencias` and `tutoria` use their existing empty valid payloads, with the label "Sin registros sintéticos en esta demostración", and do not imply that any requirement is met. The Profile screen in profile mode shows identity from `formulario`, plus "Datos personales no disponibles para perfiles sintéticos" when `perfil === null`.

## Exact interface deltas against the drafts (applied)

- **HTTP:** LPD keeps exactly `GET /local/perfiles/v1/perfiles` and `GET /local/perfiles/v1/consultas/:key?runId&actorId&sessionId`. Session create and renew remain MR2 (`POST /local/matricula-regular/v1/sesiones`, `…/:id/renovar`). The `sesiones/:id` and `cerrar` endpoints are removed.
- **`consultas` precedence:** structure 400 → run 409 `RUN_CHANGED` → actor 404 → session 404 `SESSION_NOT_FOUND` → identity 409 `SESSION_CONTEXT_MISMATCH` → expiry 409 `SESSION_EXPIRED` → projection (internal 500 `LOCAL_FAILURE`). No new error code.
- **Shared module:** remove `SessionView`, `ClosedSession`, `validateSessionViewResponse` and `validateClosedSessionResponse`. Use the MR2 `validateSessionResponse`. `DashboardPayloadMap` adds `perfil: null`.
- **Store (`localProfileSession.ts`):** snapshot = `anonymous | entering | active | expired | error`. `active` and `expired` hold `{runId, actorId, sessionId, startedAt, expiresAt, deadlineMono, formulario, generation}`.
  - Methods: `enter(actorId): Promise<void>`, `renew(): Promise<void>`, `logout(): void`, `observe(serverNow: string): void`, `markExpired(): void`, `markRunChanged(): void`, `getSnapshot()`, `subscribe(listener)`.
  - Store state is never written to any browser storage.
- **Countdown anchor:** on receipt of any validated `serverNow` (S) at monotonic time T_r, `deadlineMono = T_r + (expiresAt − S)`. For `create`, S = `startedAt`; for `renew`, S = `expiresAt − 900000`. Because S was computed before T_r, the client deadline is always ≥ the true server deadline, so the client never expires early, and the server rejects anything after its own deadline.
- **Late responses:** each request captures `generation`. A result whose generation is not current is discarded even if the abort was ignored.

## Clarification LPD-DEC-1a (2026-10-14, implementation detail, no scope or wire change)

Requested by the coordinator (task `task_88199a378988`, dispatch `ctx_dc7d28963394`). Backend/shared wire stays frozen. These points refine D1 and D3. Where they differ, they replace the D1 wording "every store transition increments generation" and the summary "store becomes `expired`".

1. **Generation and router reload only on identity change.** `generation` changes only when the identity tuple `(runId,actorId,sessionId)` changes:
   - `enter()` success: none → tuple. From `expired`, `enter()` first performs the logout transition.
   - `logout()`: tuple → none.
   - `markRunChanged()`: tuple → none.

   Only these run `router.clearCache()` and `router.invalidate()`. Anchor-only updates never touch generation or the router: `observe(serverNow)` from any `consultas` read, renew success (same sessionId), countdown ticks, `markExpired()`, and `entering`/`error` states. Root `loaderDeps` is `{generation}` only, so anchor updates re-render subscribers such as the Shell countdown without re-running loaders, which avoids loader loops. A stale-generation `serverNow` is ignored. Tests: `observe_no_loader_rerun` (N reads plus ticks give 0 extra loader calls) and `identity_transition_clears_cache` (each of the three transitions clears the cache exactly once).
2. **`perfil` takes the direct typed route.** In profile mode the `perfil` route calls the typed dashboard API directly (`read('perfil', identity)` → `null`) and renders identity plus "Datos personales no disponibles para perfiles sintéticos", the same pattern as the six academic keys. That makes 7 route-direct keys. The other 7 compatible keys (`formulario`, `historial`, `fichaSocioeconomica`, `evaluaciones`, `deudas`, `asistencias`, `tutoria`) use the `sumApi.get` profile branch, which unwraps the validated payload. `sumApi.get`'s signature and `ApiResponseMap` are unchanged. A profile-mode `sumApi.get` for a route-direct key throws before fetch and never falls back to mock or legacy.
3. **Expiry guard exception.** `markExpired()` keeps the tuple.
   - If the current route is `/local/matricula-regular`, that already-mounted screen stays and offers only manual MR-RESULT consult of its restored intent (no selection, submit, renew or report navigation).
   - On any other route, the root navigates immediately to `/local/login` with an expiry notice (navigation, not invalidation).
   - While `expired`, `beforeLoad` sends every protected navigation to the chooser, including `/local/matricula-regular` and its report child. The single mounted enrollment screen is the only exception.

   Test: `expired_guard_exception` covers expiry on Home (goes to login), expiry on the mounted enrollment screen (consult GET allowed, 0 POST), and any later navigation (goes to login).

Approved scope is unchanged: the user-approved simple four-profile form, the legacy 001 counts and ledger, and the integrated LP-R1 are not affected.
